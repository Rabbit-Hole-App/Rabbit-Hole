# Topic pipeline

The [specification](SPEC.md) and [SOP](SOP.md) are the source documents for this pipeline. The Reviewer owns both documents and the working agent prompts. Replace supplied document revisions verbatim.

Install the web workspace dependencies and run `npm ci --prefix scripts/topic-pipeline`. Copy `scripts/topic-pipeline/config.example.json` to `config.local.json` in the same directory. Fill all keys, operator paths, prices and endpoints there. Paths are relative to the local config file. Credentials are read from that file, and the config is ignored by git. Fixture inputs and recordings belong under the topic fixture directory. Keep operator files outside the authored worktree.

Run `node scripts/topic-pipeline/run.mjs logistic-regression --from 02 --to 02`. State and outputs go under the configured topic root in `logistic-regression/`. A completed stage is skipped on resume. An explicit `--from` archives that stage and every later stage's recorded artefacts under `history/` before rerunning. A concurrent run of one topic is refused.

The four stops follow SPEC §7. `--approve-prompts` stops after 01 at STOP-1. Exhausted verification stops at STOP-2 and resumes from 03. Pack failures and audit holds stop at STOP-3 and resume from 06. Stage 08 writes READY.md and stops at STOP-4. Only `run.mjs logistic-regression --go` after STOP-4 can enter 09.

Stage 02 uses the existing live planner and the same shared selector call as the server. Planner-derived `plannedKinds` and learner-requested `requiredKinds` retain their separate live meanings. A gallery shape cannot count as REUSE. The same worked source must appear first with the expected kind at all three depths and the injected coverage judge must agree. Deliverable 1 reads judge booleans from `fixture/coverage-judge.json`. A recorded planner fixture may be configured with `planner.fixtureFile`, keyed by the exact prompt and then the live depth names. Without that fixture the planner is a model call using the local config.

In fixture mode for Lesson 04, shipped `ml-trees-*` references are excluded before topical scoring and steering. The later author loop reserves `topic/decision-trees-dryrun`, modules named `topic-decision-trees-dryrun-*`, and ids prefixed `ml-dry-trees-`, as required by SPEC §4. Its separate worktree and permission-restricted test execution are part of deliverable 3.

The bench, sets, pack exporter and slug index come from the tooling checkout named by `repo.toolingRoot` at `repo.toolingRef`. They are called in place. The default is now `main`: release 121 (`092cd688b`) includes the bench merge, completing the tooling-ref transition specified in §6c. An explicit local tooling pin remains supported.

Run the required offline suite with `node --test scripts/topic-pipeline/**/*.test.mjs`. Provider calls are mocked in tests. The reference linter joins this suite and is also a standalone command, `node scripts/topic-pipeline/checks/reference-linter.mjs <module path>`. Rules 2, 6 and 9 produce warnings for pre-existing modules and errors for pipeline-authored modules. Rule 2 permits retained long phrases when `shortKeywords` supplies 2–3 lowercase learner entries of at most three words each, or `keywords` supplies at least two such entries. A green offline suite establishes the contracts and fixture wiring. The Reviewer supplies the Lesson 04 human scoring fixtures and reviews each push before stack operation.

Stages 01, 04 and 07 run independently with `--fixture --from 01 --to 01`, `--fixture --from 04 --to 04`, and `--fixture --from 07 --to 07`. Stage 01 reads the topic.json source metadata and the audited curriculum revision or configured source root. Stage 04 reads the union of references.human and references.defective, preserving historical id@revision identities. Stage 07 compares the saved human pack card images, body and pipeline with reference-408.svg. These modes call the configured agents. Tests inject mocked clients and use synthetic input files, with no provider calls.

The working agent prompts live in `scripts/topic-pipeline/agents/prompts/` and cite the specification and SOP sections they implement. Edit those files in place after the first fixture run. The client uses Anthropic Messages with vision for reviewers and OpenAI Responses with reasoning.effort max for the author. Override reviewer, author and judge models with their CLI flags and configure prices for each selected model. Preflight rejects a full-topic estimate over perLessonUsd. Every attempt is charged before schema validation, including the one permitted retry. Unknown usage blocks further calls until reconciled. Actual spend over 1.2 times the estimate aborts the run.

Topic naming follows SPEC §2a. The unchanged config and stage examples in §§3–4 still contain lesson-named fields, modules and commit text. Runtime schemas use a topic slug and prompt origin metadata. The source spec is preserved verbatim for the Reviewer to amend.

Stage 03 creates a separate topic worktree from repo.releaseBranch and writes only schema-approved topic files. Static rule 11 runs before authored files are written or imported. Arithmetic tests and reference evaluation run in a child with an empty environment, worktree-only Node permission grants, no child-process or worker grants, and a ten-minute timeout. The runner uses test isolation none so Node's test runner does not need child-process permission. Each round retains the verbatim feedback and a commit. The author manifest includes the actual replay, prior-pick and paraphrase results. A REUSE overlay targets the original registry id even when the author receives its single-diagram variant.

Stages 05–09 call configured commands and the pinned bench and pack exporter. Fill integration.commands and propertyCountCmd with the existing required gates. Set bench.estUsdPerCard for bench admission. Missing required commands fail with a clear no-op message. Saved bench runs can be supplied in bench.fixtureRuns for offline pack replay. The real saved demo run acceptance test remains skipped until its results.json/raw directory is supplied. The pinned judge's hardcoded credential-file transport must be made compatible with the config-only rule before live judged packs can run. The pipeline refuses that transport.

The decision-tree dry run uses a throwaway release/dryrun-decision-trees integration branch and ends at stage 07. Fixture mode selects the human comparison inputs and masks shipped tree references during coverage. Provider and stack operations still require a configured, reviewed run. Preview deployment and release are excluded from a dry run. Operational stage 07 regenerates selected variance once, and any factual hold stops at STOP-3. Stage 08 writes the preview and record list, then STOP-4 requires the explicit --go to invoke the release launcher. The queue remains an array of topic/lessons entries, with completed entries removed after a successful release.

For Lesson 03, run `node scripts/topic-pipeline/run.mjs logistic-regression`. Stage 01 reads an existing topic.json or initializes one from the pinned tooling slug index, using the configured audited curriculum path template and revision. A topic with owner or learner sources supplies its own topic.json and configured sourceRoot. Topic metadata is input and survives stage reruns.

Extract the original Lesson 04 specs and previews with `node scripts/topic-pipeline/checks/extract-fixtures.mjs decision-trees --config scripts/topic-pipeline/config.local.json`. The checked-in fixture assets contain 45 corrected previews and 17 historical previews for the seven requested defective cases. All 124 spec/SVG blobs are copied from git history byte for byte. Repeating extraction preserves equal files and refuses to overwrite different Reviewer content. The extractor does not invent verdict mappings.

The Reviewer still supplies prompts.human.json, verify.human.json, audit.human.json, pack.human, and references.defective/expected-verdicts.json. Run `node scripts/topic-pipeline/run.mjs decision-trees --dry-run --fixture` after configuring the approved tooling and local stack. The run ends after 07 and writes fixture-score.json. It uses the same verifier prompt file for teaching-point mapping, compares human and authored verification separately, and scores the human and authored packs separately. Missing or ambiguous inputs produce unscored with exit 1. The checked-in fixture-score.json records that current missing-input state and establishes no agent agreement.

The scorer can also run alone with `node scripts/topic-pipeline/checks/fixture-score.mjs decision-trees --config scripts/topic-pipeline/config.local.json`. Targets are the literal pilot 8/10 agreement plus the mandatory 48ths/depth defects, prompt overlap 9/12 with kind agreement 80%, paraphrase first-pick 80%, pack references 12/12 and kind 11/12, and human audit agreement 11/13 with the three mandatory card verdicts. The static linter cannot establish leaf/depth arithmetic or historic SVG tick formatting by itself. Those remain vision-verifier responsibilities.
