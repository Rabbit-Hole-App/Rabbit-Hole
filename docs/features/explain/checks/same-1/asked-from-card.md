# SAME-1 c: where a card asked FROM a card could pass its parent's diagram kind and reference id to the planner and selector as "already shown" (report only, no code; main 2aeca536d)

## What a card asked from a card sends today
1. Client, the three destinations that make a card (`card`, `follow-up`, `explore`): `packages/web/src/AdaptiveCanvas.jsx:6463-6476` (`hostRef.current.ask`). It finds the parent block (`blocksRef.current.find(id)`), builds `selection = { id, title, text, explanation: { revision, actionId }, parentLink?, beside? }` where `text` is the parent's title + body + folded sections, cut at 8000 characters (`:6468`), and runs `chatWorkspace.ask({ line: '/explain <question>', about: { selection } })`. `explore` builds the question text in `explanation-interactions.js:43-51` (`In the context of "<title>": what is "<term>" ...`, at most 220 chars); `card` and `follow-up` send the suggested question or typed text as is.
2. Dispatcher: `ask.jsx:988-989` (`registerSender`, `line` + `about`) -> `LearnSlash.jsx:105` (`handoff`) -> `exec` -> `run(...)` with `target = about.selection`. In `learn-slash.js`: `:331` (`canvas.startExplain(explainWords, { context: target.text.slice(0, 8000), ... })`, the LearnPage job route) or `:338` (`generateCommand(... { selection, context: explainContext(target) })`, POST `/api/learn/artifact`, `:200`). Both carry the parent's text as `context`. LearnPage's job payload (`LearnPage.jsx:1207`) is `{ prompt, requestClass, source, context: { text }, ... }`.
3. Server (the /api/learn/artifact route that wrote the archive records): `learn-artifact.js:397` validates `body.context` (a string), `:453` archives only `hasContext: Boolean(body.context)` and `sourceRefId` (a source-document passage id from R3, not a card). `prepareArtifactAuthorRequest` -> planner: `learn-artifact.js:187` `planExplanation(env, { question: input.args, depth, context: input.context })`; `explanation-planner.js:129` sends the planner `state.context = String(context).slice(0, 2000)` (the first 2000 characters of the parent's title + body). Selector: `learn-artifact.js:137-141` `selectForAuthor({ prompt, context: { selection: request.selection, context: input.context, documents }, asked, planned, depth, plan })`; `explanation-references.js:151-157` -> `selectWithSteer({ prompt, context, depth, requiredKinds, plannedKinds, shapeFallback, excludeReferencePrefixes })` (`:93`). Context only adds scoring words there.

## Where "already shown" could be passed
- **Selector:** `selectWithSteer` already has an exclusion input, `excludeReferencePrefixes` (`explanation-references.js:93`, `selectForAuthor :151`, `planWithReferenceKind learn-artifact.js:159,164`). The natural place for "the parent already shows reference X / kind K" is next to it: an `alreadyShown: { kinds, referenceIds }` in the same option object, filled in `learn-artifact.js:137` and `:164`.
- **Planner:** `planExplanation(env, { question, depth, context })` (`explanation-planner.js:124`, called `learn-artifact.js:187`): a fourth field in `state` at `:129` (`parentKinds`) beside `context`, and one clause in the planner's instructions.
- **Client origin:** the `selection` object built at `AdaptiveCanvas.jsx:6471` is where the parent's kind and reference id would be added (the block is in hand there, `card`), and `learn-slash.js:331/338` is where it would be copied into the request (`selection` is already sent by `generateCommand`; `context` is a plain string).

## Is the parent's block readable server-side at that point?
- **Its text, yes, as a string:** the parent's title + body (including its `rh-diagram` fences, with `"kind": "..."` inside the JSON) arrives as `context` (client-capped at 8000 characters; the planner reads the first 2000, the selector reads it as scoring text). So the parent's diagram KINDS could be derived server-side by parsing the fences in `context`, if the body is not cut before them (a long body could be cut at 8000; the planner's 2000-character slice can cut before the diagram).
- **Its reference id, not found in the request:** the request carries the parent's block `id` (`selection.id`) and `revision`, but nothing in `/api/learn/artifact` or the job route looks the parent block up by id (no store read of the parent in `learn-artifact.js`; `explain-job.js` only resolves `context_refs` through `resolveEditRefs`, `:328-331`, source references, not canvas cards). The archive stores `references` and `plannerKind` per request (`learn-artifact.js:199` trace, `archive :451`) keyed by the archive record's own id, and the card block built from the answer (`artifactBlock`) was not found to carry the reference ids or the planner kind. So the reference id would have to be added when the card is made (stored on the block) and sent back from the client at `AdaptiveCanvas.jsx:6471`; or the parent's kind could be read from the fenced JSON in `context`.
- Not verified: whether a parent's block on the canvas carries a hidden field for references or `plannerKind` (the explanation block shape was not read end to end); the three SAME-1 archive records show only `hasContext: true`, so the parent text itself is not in the archive.
