## ml-transfer-learning-modality-feature-classifier

A visual backbone can pass a learned vector to a classifier just as a text encoder does. Preserve two modalities, their distinct feature extractors and one feature-vector-to-classifier pattern. The frozen native relationship graph requires a **connected** graph, so two independent modality paths cannot be placed there without an invented relation; do not add a false fusion or analogy arrow merely to satisfy connectivity. Overview is a small categorical matrix comparing the two extractors/readouts. Standard is a fuller native matrix with one row per modality and explicit input, extractor, feature-vector and classifier columns. Deep shows a native block-stack for the text path (extractor -> structural vector -> own task head), with a separate native image-path block-stack as detailSpec. Symbolic feature lists derive the respective two-cell and three-cell shapes: the same recipe does not imply the same feature coordinates, width or classifier parameters. Both modalities, extractors, vectors and heads remain explicit across these supported full-width views. No measured feature values or transfer-performance claims are needed. Keep topic transfer-learning and lessons01/08. The existing CLS-readout Deep detail has a text/image feature-source table, but its ordinary main views teach CLS selection, not this modality analogy; the multimodal competitor instead merges front ends into one generative decoder. Neither is a faithful ordinary-route REUSE of the queued point.

Suggested learner keywords: `modality classifier pattern`, `feature extractor analogy`. useWhen: “Compare text and image feature extractors feeding their own task classifiers through learned vectors; not multimodal fusion, a shared text decoder, shared feature coordinates, or a claim of equal task performance.”

## ml-bert-pretraining-lineage

BERT belongs to a line of work that combines reusable language representations with Transformer encoders. Contrast the Transformer architecture with independently described pretraining approaches, then place BERT among them without inferring performance from chronology. **REUSE `ml-bert-pretraining-families`**, whose native matrix already compares original translation Transformer, ULMFiT, ELMo, original GPT and BERT by architecture and training objective. Overview uses plain “how it reads/what it learns” labels; Standard distinguishes encoder–decoder translation, forward LSTM, independent directional LSTMs, causal decoder and bidirectional encoder; Deep notes original BERT's sentence-pair objective and explicitly separates architecture from objective. This supplies the intended contrast more faithfully than manufacturing a timeline that could imply “later means better”. Add the source statement verbatim and narrow keywords through the supported overlay; keep every existing visual/data byte and original production depth fallback. Its existing lesson01 already matches. No extra numeric history, benchmark or invented date is necessary, and a new composition would duplicate a complete native-kind explanation.

Suggested added keywords: `pretraining encoder lineage`, `architecture objective lineage`. Existing useWhen remains unchanged under REUSE; association exclusions: not a performance ranking, Transformer-XL memory comparison or a claim that all pretraining methods use bidirectional encoders.

## ml-bert-summary-token-readout

Preserve all token positions, a marked summary position, the vector selected from that position, a learned linear classifier, independently specified sample class scores and their interpretation. **NEW computed readout across native full-width views**, keeping the original `ml-bert-cls-readout` unchanged: that legacy reference does identify CLS, but its outputs are text-list percentages (“Wildlife 70%”, “Repair 30%”), not magnitude-encoded scores, and it provides neither a selected numeric contextual vector nor weights/bias to recompute the merged Figure10 operation. Overview is a full-width heatmap with every token row and marked CLS, showing only the first toy feature; state explicitly that it is one displayed feature rather than the complete representation. Standard is a full-width heatmap of all declared feature columns, with the same rows/CLS mark and a visible data-derived description of selecting that row and applying the declared linear head. Deep is a separate full-width class-score bar chart, with the selected CLS vector, W/b and computed `z=hW+b` operation/result visible in the caption. Its one detailSpec is a full-width probe heatmap: already-encoded non-CLS rows change while CLS, head and resulting class scores stay fixed. Use a common explicit heatmap range for the base/probe, with the unchanged result stated from recomputation. This conditional probe does **not** mean other input words are irrelevant: changing words before encoding can change CLS. Keep source lessons01 and alias03 individually traceable and catalog union01/03. Dense heatmaps must never be crushed into ordered half-width panels as the rejected first C03 draft was; the owner-approved depth split carries the selection and numeric result without a new renderer or text-box workaround.

The proposed Standard is a native heatmap, so it has **no linked single variant**; its ordinary author route sends the native id and actual depth-resolved view. The other two NEW Standard designs are also native matrices. Accordingly this accepted proposal would add **no new eligible composition parent and no new set3 pair**, while still requiring canonical per-view token/hash receipts and actual prepared author-schema validation for every source prompt/depth. If implementation later changes any Standard into an eligible comparison/panels form, its same-point supported single and paired receipts become mandatory; that change must not reintroduce the dense-heatmap scaling problem.

Suggested learner keywords: `summary row projection`, `contextual readout scores`. useWhen: “Select the designated contextual summary row from aligned encoder outputs and compute task scores with the declared linear head; not raw token-embedding lookup, average pooling, token tagging, or treating class scores as probabilities.” Avoid existing concise CLS question phrases so their old picks remain unchanged.
