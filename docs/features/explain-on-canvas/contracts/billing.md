## 3. Trusted server-only operation identity: `withRoadmapProviderCall` (patch DESCRIPTION, not applied)

Gap: `spendTransport` always generates a fresh random `opId` (`learn-spend.js:78`) and `anthropic()` passes it no identity beyond `provider` (`ask.js:311`). The checklist (R4.06) and v1.4 5.1 require a stable ID that reaches the transport that performs admission, not an unused `attemptId` argument, and that caller input cannot choose. Final main (`9b798f776`) did not change these lines: `spendTransport` is still `learn-spend.js:66`, the `opId` mint `:78`, `askJev`'s mint `learn-grade-jev.js:150`; P1 moved `spendCallModel` to `learn-spend.js:150`, so R4 wraps through that retained helper and never imports the retiring Tutor routes.

Public name (checklist 2.1): `withRoadmapProviderCall(env, { proposalId, proposalVersion, cardId, stage, call, retry, authorizationId })`. It validates the fields with `operationKey()` from the contract module (server ids, `PROVIDER_STAGES`, small integers), derives `operation_key = rm.<proposalId>.<proposalVersion>.<cardId>.<stage>.<call>.<retry>.<authorizationId>`, hashes it to the ledger `op_id` (sha256 hex, 32 characters, prefix = stage), and returns a copy of `env` carrying it, bound to the serialized request/model/provider fingerprint. Patch (Lead-only `learn-usage.js`, plus `learn-spend.js` and `learn-grade-jev.js`; a Symbol-on-env carrier is how `withAttemptKind` already travels through `generateArtifact` without changing any `callModel` signature, `learn-usage.js:97`):

1. `learn-usage.js`: a private `OPERATION` Symbol with `withOperationId(env, id, fingerprint)` / `operationIdOf(env)`; only `withRoadmapProviderCall` calls the former. A Symbol cannot be set from JSON, a header or a query.
2. `learn-spend.js` `spendTransport`: `const opId = operationIdOf(env) ?? operationId(...)`, validated against `^[a-z0-9._-]{16,120}$`; the carrier is consumed once and removed from the env handed to `transport`, so a nested admission or retry cannot reuse it. Keep the existing single-call `admission` token so a wrapper and the underlying transport still admit once. A request whose fingerprint differs from the one bound to the op id is refused.
3. **Replay handling** (not optional): `admitSpend`'s two `catch` blocks turn a primary-key violation on `usage_operations.op_id` into `spend_schema_unavailable` / `allowance_unavailable` (`learn-spend-ledger.js:78-80,94-96`). With stable ids a duplicate must be detected first by reading `learn_learn_roadmap_calls` and `usage_operations`/`usage_attempts` by `op_id`: `settled` returns the persisted output (`output_ref`), never another provider request; `admitted`/`dispatched`/`unknown` returns "in flight" and enters reconciliation (section 6). Never silently re-send.
4. `askJev` (`learn-grade-jev.js:139-151`): apply the same convention to its independent admission, with the internal 429/529 capacity retry as its own `retry` index (the safety screen is platform work).
5. Tests (failing on old code): same id twice -> one `usage_operations` row, one provider call, the second returns the recorded outcome; nested wrapper + transport admit once; an id taken from a header or body is ignored; forged or malformed ids refused; JEV retry ids distinct; restart after admission; two different ids in one action are two attempts (R4.06's named suites `roadmap-provider-identity.test.js`, `roadmap-quotas.test.js`, `learn-spend.test.js`, `learn-usage.test.js` must assert the actual admitted op ids).

Durable call checkpoints (contract `CALL_CHECKPOINTS`, table `learn_learn_roadmap_calls.checkpoint`): planned -> admitted -> dispatched -> response_recorded -> settled, with explicit `unknown`/`reconciling`. `generateArtifact` makes up to two calls per card (first + repair): the adapter wraps `callModel` to call `withRoadmapProviderCall` per call with `call` 0 then 1; a generic "generate" id reused for both is insufficient (R4.08).

## 4. Aggregate allowance admission (D6, 5.2, R4.07): what must exist

Requirement: before consuming acceptance or dispatching any card, atomically admit/reserve the whole step under one authorization; insufficient allowance leaves the proposal `pending` and nothing consumed; per-card allocation recorded; per-call admission consumes or transfers the allocation instead of reserving twice; unused allocation released at completion or terminal failure.

What exists: only a read-and-compare. `ExplainJobs.admitGeneration` (`explain-job.js:391`) checks `allowance - used` against the worst case, and its header says "that is a check, not a hold (a hold plus per-call admission would count twice in HELD_SUM)... Upgrade when the ledger can admit calls against a parent hold" (`explain-job.js:11-14`). So the parent hold is **not supported by current code**.

Checklist design (R4.07; adopted over the first draft's `usage_attempts` hold row, see `checklist-map.md`): three tables in the second migration, `learn_step_authorizations`, `learn_step_allocations`, `learn_step_allocation_transfers` (`roadmap-r4-authorizations.draft.sql.txt`), and:

- `admitStepAuthorization(access, proposalVersion)`: the winning acceptance batch (`acceptRoadmapStep`). It validates the current checked proposal, access and immutable bounds, tests the **full-step** allowance and writes the authorization, the per-card allocations, the acceptance binding and the replay outcome as one D1 batch guarded by the same winning receipt (not by an earlier balance read). Insufficient allowance writes no consumed acceptance and no purchased card; the route answers the existing refusal body (`allowance_limited`, 429), proposal still `pending`.
- Stored amounts: integer micros, payer, period, aggregate bound, per-card bound, remaining unallocated balance, immutable content/format bounds, authorization deadline. The offered envelope is the worst case over permitted generation/repair/retry stages; platform-paid checks are separate. A material expansion needs a revised proposal and a new acceptance (D38).
- **One shared balance definition.** Available = allowance - settled net charges - outstanding ordinary call holds - the remaining untransferred step holds. That means editing `learn-usage.js` `BALANCE_SCOPE` / `USED_SUM` / `heldSum` / `usageTotals` (lines 447-490, Lead-owned) and the allowance clause of `admitSpend` (`learn-spend-ledger.js:35`) to include `SUM(remaining_micros)` of `learn_step_allocations` for the payer and period, so Settings usage and every other Chat call see the same held amount.
- `consumeStepAllocation` inside `admitSpend`'s atomic batch for a trusted authorized call: verify allocation ownership/version/bound, admit the platform expense (`PLATFORM_INSERT`), decrease that allocation's remaining hold, insert the call's own `usage_attempts` reservation and one `learn_step_allocation_transfers` row (unique `op_id`). The transfer replaces an equal part of the hold; a platform refusal or any failed guard statement transfers nothing; a replay cannot transfer again. Arithmetic invariant for the Verifier: `remaining step hold + transferred call holds <= the admitted amount` at every boundary.
- Release: unused allocation on card completion or terminal failure; preserve other in-flight cards' reservations; a late response cannot resurrect a released hold or charge beyond authorization.
- Step deadline must stay inside the usage hold window: `releaseStaleHolds` seals running attempts after `HOLD_SECONDS` (`artifact` 3600 s) as failed/unknown (`learn-usage.js:286-296`). `ROADMAP_LIMITS.deadlineMs.stepWork` is 660 s and the policy test requires it below half the window.
- Platform side is separate: every per-call admission still passes the platform guard; the learner hold does not replace it.

Alternative considered and not adopted: a single `usage_attempts` row of kind `tool` as the hold (no new tables, no balance-SQL change, because `heldSum` already counts it). It is smaller but puts a synthetic attempt in Settings usage by feature, cannot carry per-card allocations or the transfer uniqueness, and the checklist chose tables. If the Lead prefers it for R4 it satisfies the same invariant with `parentHold` decrementing that row; say so in the prerequisite receipt.

If State will not touch `admitSpend` in R4, the safe fallback is the aggregate **check** (not hold) as `ExplainJobs` does; it breaks "insufficient allowance consumes nothing" only for the narrow race of another spend between Tab and the first call, and must be named in the R4 receipt. Recommended: build the hold.

## 5. Quota reservation counters (D14)

Existing guard is global (`platformCaps`: operations per day default 2000, USD per day, `learn-spend-ledger.js:9`). Per-learner work quotas do not exist. Contract: table `learn_roadmap_quota (org, owner_user_id, scope, window_start, calls, micros)`; before each platform call run `INSERT ... ON CONFLICT DO UPDATE SET calls = calls + 1 WHERE calls < ?` and refuse (typed `quota_exhausted`, learner sentence in `ui.md`) when it changes nothing; after the call settle or release (`calls - 1` only when the provider was not reached). Scopes in R4: `plan` (drafts+revisions), `propose`, `check`, `invite`; windows hour and day; limits live in `ROADMAP_POLICY` (proposed numbers are provisional and not budget approval, D14). A crash between reservation and call leaves the counter incremented until the window ends: conservative, acceptable. Not atomic with `admitSpend` (separate batches): the order is quota reserve -> `admitSpend` -> call -> settle -> quota settle.

## 6a. Atomic refund and result transition (checklist R4.11)

The refund and the result's `billing: settled -> refunded` transition (and the replay receipt) must be one guarded batch. Calling `refundAttempt` and then updating the result row is two commits and may not be described as atomic. Required: a roadmap refund helper (in `roadmap-money.js`) that issues the `usage_attempt_detail` refund UPDATE (same guard as `refundAttempt`: `refunded_micros = 0`, attempt `settled`, cost > 0), the `usage_adjustments` audit INSERT, the `learn_step_results` billing update and the action receipt in a single `db.batch`; the generic `refundAttempt` keeps its behavior for other callers, so its audit gap stays but is closed on this path. Refund per attempt only: `refundActionByKey` refunds every settled attempt of an action and is unsafe for a step whose delivered siblings keep their charges. A failure class and its stage are persisted (`FAILURE_CLASSES`, `failure_class`) before any retry; only `transient_provider_failure` earns the one automatic retry, after the card's charges are refunded and any unused hold released; provider operations are never deleted or rewritten, and an unknown attempt stays zero-charged to the learner (`learn-usage.js:453-458`) while the provider uncertainty is tracked separately.

## 7. What the ledger records versus what the learner is charged

R4 learner charge = the settled provider cost of the learner-payer attempts (`USED_SUM`, `learn-usage.js:451`), identical to every other chargeable feature today (price version in `usage_attempt_detail`, `notePrice`). There is no separate learner price, no result-to-operation mapping and no `admitLearnerCharge`; those are R11 (v1.4 5.3). Do not build them in R4. Users see AI credits only (CLAUDE.md standing rule): nothing in `RoadmapView` carries dollars, micros, models or prices (api.md 6).

## 8. Where existing code does NOT yet support the contract (State's plan list)

1. No caller-supplied operation id; `opId` is random per call (`learn-spend.js:78`). Needs section 3 (`withRoadmapProviderCall`).
2. A duplicate `op_id` is reported as an unrelated refusal (`learn-spend-ledger.js:78-80,94-96`). Needs section 3.3.
3. No parent hold / transfer; the explain job documents it as a known shortcut (`explain-job.js:11-14`). Needs section 4 (`admitStepAuthorization`, `consumeStepAllocation`, and the shared balance SQL).
4. No per-learner platform quota; only global caps (`learn-spend-ledger.js:9`). Needs section 5 and `learn_roadmap_quota`.
5. `anthropic()` passes only `{ provider }` to `spendTransport` (`ask.js:311`); category/kind/userId are not carried through `callModel`. The env-Symbol carrier avoids changing the signature; alternatively extend `callModel`'s identity argument (more edits).
6. `withSystemUsage` records platform work with `user_id` NULL (`learn-usage.js:117-121`): per-learner attribution of platform spend exists only in `learn_roadmap_calls`, so an owner report by learner must join that table. The owner telemetry for platform spend by learner (D15) is R11.
7. Refunds are per attempt; there is no attempt -> card mapping outside the new `learn_roadmap_calls`. The route-level `refundFailedAction` (`learn-usage.js:391`) works on HTTP failure of a request and does not apply to DO work.
8. `generateArtifact` may route to OpenAI when `OPENAI_API_KEY` and `LEARN_PLAN_MODEL` are both set (`ask.js:271`, `learn-models.js:121`): the provider, price table and admission identity change, and the learner could be charged an OpenAI-priced call. Contract: the adapter forces the `anthropic` path, or Lead pins a `roadmap_card` task (adapter.md 6). Whether the dev worker has those variables set is unverified.
9. The `artifact` task model is `ASK_MODELS.auto = 'claude-opus-5'` (`learn-models.js:14,113`), i.e. $5/$25 per MTok (`pricing-registry.js:42`), not Opus 5.5 ($4/$20, line 43) and not Sonnet. Cost estimate in `decision-records.md` uses it as the conservative bound.
10. `HOLD_SECONDS.artifact = 3600` (`learn-usage.js:461`): step deadline must stay below it (section 4).
11. `spendTransport` returns early with no admission when `SMALL_ENV === 'test'` or `SUBSCRIPTION_ONLY === 'true'` (`learn-spend.js:67,69`). Tests of money paths must set the enforcement on, as `learn-usage.test.js` does.
12. The roadmap DO runs outside a request: it needs the payer forwarded the way `forwardUsagePayer`/`usageFromForwarded` do (`learn-usage.js:254-267`, header `x-rh-usage-payer`), or the `job.owner` pattern in `ExplainJobs`; the owner identity is stored on the roadmap row at creation.

13. JEV does not go through `spendTransport`: `askJev` admits each POST itself with `operationId('jev')` (`learn-grade-jev.js:150`), so the operation-id hook (section 3) must also be applied there for the safety screen, or the screen stays unkeyed (its cost is negligible, $0.042/MTok input; the risk is only duplicate admission on a replayed stage).

## 9. Tests State must write (money)

Two concurrent accepts (one hold, one card, one charge); accept with insufficient allowance (proposal `pending`, zero rows consumed); crash at each write boundary of the accept batch (nothing half-applied: single batch); hold released on completion and on terminal failure; replay of the same op id (no second provider call); unknown outcome never resent; refund-then-retry order; refund replay (second refund is 0); held card refunded on terminal check failure; ack lost then reload (one card, one charge); Ask mode with accepted work in flight (finishes and delivers); flag off during generation and after settlement (v1.4 4.1), restored with no duplicate charge.
